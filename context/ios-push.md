# Входящие звонки: PushKit и APNs

Реализовано 26.09.2026. Сборки, тесты и отправка в APNs агентом не запускались. Проверять на физическом iPhone; симулятор не регистрирует VoIP-токен.

## Настройка сервера

Обновить backend (миграция V72 создаёт `call_push_devices`) и matrix-infra. В защищённом серверном `.env`:

```dotenv
APNS_ENABLED=true
APNS_TEAM_ID=<Team ID>
APNS_KEY_ID=<Key ID>
APNS_BUNDLE_ID=com.andreichev.matrix
APNS_PRIVATE_KEY_BASE64=<одна строка base64 всего файла .p8>
```

Получить значение последней переменной на Mac:

```sh
base64 -i /путь/AuthKey_KEYID.p8 | tr -d '\n'
```

Это секрет, а base64 не шифрование. Не публиковать результат, `.env` или `.p8` в Git, переписке и CI-логах. Ограничить доступ к `.env` (`chmod 600 .env`) и Docker. Team ID и Key ID не заменяют приватный ключ. Ключ должен разрешать APNs для приложения и используемых окружений.

После изменения конфигурации пересоздать backend обычным деплоем. Новых входящих портов не требуется; серверу нужен исходящий HTTPS/HTTP2 к `api.push.apple.com` и `api.sandbox.push.apple.com` на 443.

Для локального backend можно вместо base64 задать `APNS_PRIVATE_KEY_FILE=/абсолютный/путь/AuthKey_KEYID.p8`. Этот путь относится к машине процесса, не к телефону. В стандартном Compose используется base64; файловый вариант требует собственного read-only mount.

При `APNS_ENABLED=false` ключ не требуется, текущие web-звонки и ручное присоединение остаются прежними. При включённом APNs неверный формат ключа останавливает запуск с понятной ошибкой без содержимого ключа. Отказы Apple видны в backend-логе с кодом ответа и причиной.

## Настройка Xcode

1. Target `Matrix Workspace` → Signing & Capabilities: своя Team, Automatic signing, **Push Notifications**. Проверить, что этот App ID разрешает Push Notifications в Apple Developer и профиль подписи обновился.
2. Background Modes: **Audio, AirPlay, and Picture in Picture** и **Voice over IP**. Оба режима уже в Info.plist. Remote notifications для данного сценария не нужен.
3. `Matrix.entitlements` уже подключён. `APNS_ENVIRONMENT` в Debug — `development`, в Release — `production`; он задаёт entitlement и окружение регистрации токена. Для нестандартной конфигурации подписи проверить их соответствие. TestFlight использует production.
4. Установить приложение на iPhone, войти и разрешить микрофон. У сотрудника должны быть включены звонки и уведомления в Матрице. APNs-ключ в Xcode не добавлять.

Запрашивается только разрешение на микрофон. Обычные баннеры APNs пока не реализованы; входящий вызов показывает CallKit через отдельный PushKit-токен.

## Поведение

- Backend отправляет VoIP push при создании нового звонка приглашённым сотрудникам, независимо от открытого web-клиента. Проверяет доступ к звонкам, уведомления, членство в чате и действительность сессии одним запросом на всех получателей.
- Отправка идёт после фиксации звонка, в ограниченной фоновой очереди, не удерживает его транзакцию. При ошибке APNs сам звонок продолжает работать. Не повторяем неоднозначно завершившуюся отправку, чтобы не создавать лишние входящие.
- На один VoIP-токен хранится одна серверная сессия. Перевход обновляет привязку. Выход/отзыв сессии удаляет регистрацию, истёкшая сессия исключается из доставки. APNs 410/BadDeviceToken очищают недействительную регистрацию, не затрагивая более свежую.
- Приложение сразу сообщает каждый VoIP push в CallKit, затем проверяет приглашение через существующий WebSocket. Истёкшие/чужие/повторные приглашения не присоединяют пользователя к звонку. Вызов может обрабатываться без созданного экрана приложения.
- Ответ подключает к SFU и открывает экран звонка при доступном интерфейсе. Отказ меняет только собственное ожидающее приглашение; уже подключённого участника не отключает. Если ответили на другом устройстве, оставшийся входящий закрывается по сигнализации.
- Отмена звонка передаётся по WebSocket. Для отмены не отправляется второй VoIP push. У приглашения есть локальный таймер окончания; push содержит срок действия, а `apns-expiration=0` запрещает хранить его для поздней доставки.
- После показа входящего отправляется существующая отметка `presented`, подавляющая отложенный Web Push. Браузерные клиенты не изменены.

Доставка APNs не гарантируется. Без сети звонок не появится; принудительное закрытие приложения, перезагрузка до первого разблокирования, Focus и системные ограничения требуют отдельной проверки. Если push не пришёл, в открытом приложении остаётся ручное присоединение к действующему звонку. После ошибки регистрации повторяем её при следующей активации приложения, без бесконечного фонового опроса.

## Ручная проверка

1. Два сотрудника с разрешёнными звонками в тестовом чате. На iPhone войти; на другом устройстве начать звонок. Проверить системный входящий, ответ, двусторонний звук и завершение.
2. Повторить при свёрнутом приложении и заблокированном экране, затем проверить запуск по push без ранее созданного экрана. Отдельно проверить Debug и TestFlight.
3. Отклонить входящий; затем завершить звонок вызывающим до ответа. Не должно оставаться звонка, микрофона или экрана активного разговора.
4. Войти одним сотрудником на двух iPhone: ответить/отклонить на одном, проверить закрытие приглашения на втором. Завершение после ответа должно завершать лишь соответствующее подключение.
5. Выключить микрофон, переключить динамик/Bluetooth, завершить через системный интерфейс и вернуться в приложение.
6. Выйти из аккаунта, отозвать сессию через «Устройства», выключить доступ к звонкам или уведомления: новые входящие не должны приходить. Проверить повторный вход другим сотрудником на том же iPhone.
7. Выключить сеть до приглашения, восстановить после его истечения: старый вызов не должен подключаться. Ошибки APNs/сети не должны мешать созданию web-звонка.
